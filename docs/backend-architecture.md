# Бэкенд: правила архитектуры

Постоянные правила для `services/*` и общих пакетов. Этапы работ, карта сервисов и модель данных — в [backend-plan.md](backend-plan.md). Если правило мешает, его меняют здесь и фиксируют причину, а не обходят в коде.

## 0. Принципы

1. **Микросервисы по ограниченным контекстам.** Сервис = контекст предметной области (каталог, газета, отзывы), а не таблица и не слой. Мелких «наносервисов» не делаем: сущности, которые меняются вместе, живут в одном сервисе.
2. **Сервис владеет своими данными.** Своя база, к ней ходит только он. Чужие данные — через API владельца или локальную копию по его событиям.
3. **Все межсервисные контракты — в пакете `@wine/contracts`.** Публичный HTTP API (OpenAPI), внутренние вызовы (protobuf/gRPC) и события (схемы). Сервисы не импортируют код друг друга — только контракты.
4. **Контракт сначала.** Сначала меняется контракт, потом реализация. Ответ, не совпадающий со схемой, — ошибка сервера.
5. **Независимый деплой.** Любой сервис собирается, тестируется и выкатывается отдельно. Изменения контрактов — только обратно совместимые.
6. **Отказ соседа — штатная ситуация.** Таймауты, повторы с экспонентой только для идемпотентных вызовов, деградация вместо падения (нет вина для стикера — статья всё равно открывается).
7. **Скучные надёжные решения и работа из России.** Стабильные версии, официальные возможности фреймворков. Хостинг, БД, брокер, почта, SMS — у российских провайдеров, персональные данные — в РФ (152-ФЗ).

| Окружение | Docker Compose на арендованном VPS (разработка и прод) → Managed Kubernetes, когда понадобится масштаб | Сервисы с первого дня 12-factor: конфиг из env, health-пробы, корректное завершение |

## 2. Репозиторий

```
apps/
  web/                       фронтенд
services/
  catalog/  news/  reviews/  newsletter/  identity/
packages/
  contracts/                 @wine/contracts — ВСЕ контракты
    openapi/                 openapi.yaml + сгенерированные типы (paths) и zod-схемы
    proto/                   *.proto внутренних gRPC-API (buf.yaml, buf.gen.yaml) + сгенерированный TS
    events/                  типы событий (CloudEvents type) и zod-схемы их данных
  service-kit/               @wine/service-kit — общая техника сервисов (не бизнес!)
  demo-data/                 @wine/demo-data — данные из макетов: фикстуры MSW и сиды сервисов
deploy/
  compose/                   docker-compose: Postgres, NATS, Traefik, сервисы, наблюдаемость
  traefik/                   маршруты /api/* → сервисы
```

- Пакеты подключаются как `workspace:*`. `apps/web` берёт из `@wine/contracts` только `openapi`.
- `services/*` не импортируют друг друга и `apps/web`. Общее — только `@wine/contracts`, `@wine/service-kit`, `@wine/demo-data` (последний — только в сидах).
- `@wine/service-kit` — конфиг, логи, OTel, фильтр ошибок, health, клиенты gRPC с дедлайнами, outbox/inbox, публикация и подписка на события. Доменной логики и типов предметной области в нём нет.

## 3. Контракты (`@wine/contracts`)

### 3.1 Публичный HTTP API

- Источник правды — `packages/contracts/openapi/openapi.yaml` (OpenAPI 3.1). Его реализуют сервисы вместе: каждый путь принадлежит ровно одному сервису (таблица в плане), Traefik маршрутизирует по префиксу.
- Каждый обработчик объявляет схемы из контракта на вход (`@Body({ schema })`, `@Query({ schema })`, `@Param({ schema })`) и выход (`@ContractResponse(schema)` из `@wine/service-kit`). Схема ответа — allowlist: лишнее отрезается, несоответствие → 500 и баг в логах. Голый `@SerializeOptions({ schema })` не используем: сериализатор Nest проверяет массив поэлементно, и схему-массив из контракта (`zGetGrapesResponse`) надо разворачивать до элемента — `@ContractResponse` делает это сам.
- Тест покрытия: каждый `operationId` реализован ровно одним сервисом с тем же методом и путём.
- Префикс `/api`, без версии в пути. Ломающее изменение — `/api/v2` для затронутых путей.
- JSON — camelCase. Даты — ISO 8601.

### 3.2 Внутренние gRPC-API

- Один `.proto`-пакет на сервис с версией в имени: `wine.catalog.v1`. Сервис-владелец реализует, остальные — клиенты.
- Методы крупные и пакетные (`GetWineSummaries(ids)`), без чатти-вызовов в цикле.
- Совместимость — правила protobuf: поля не переиспользуются и не меняют тип, удаление — через `reserved`. `buf lint` и `buf breaking` против `main` в CI.
- Каждый вызов — с дедлайном (по умолчанию 1 с), повтор — только для идемпотентных методов. Ошибки — стандартные gRPC-коды (`NOT_FOUND`, `INVALID_ARGUMENT`, `UNAVAILABLE`), без текстов для пользователя.
- Внутренние API наружу не публикуются: gRPC-порты доступны только в сети сервисов.

### 3.3 События

- Имя типа — `ru.wine-boutique.<сервис>.<факт-в-прошедшем>.v<N>` (`ru.wine-boutique.reviews.letter-received.v1`), конверт — CloudEvents 1.0, данные — zod-схема из `packages/contracts/events`.
- Событие — факт, который уже случился, с данными, достаточными подписчику без обратного вызова (event-carried state transfer, но без лишних ПДн).
- Совместимость: в версию `vN` только добавляются необязательные поля. Иначе — новый тип `vN+1`, старый публикуется параллельно, пока есть подписчики.
- Subject в NATS — `<сервис>.<факт>.v<N>`. Поток JetStream на сервис-издатель, durable-консьюмер на сервис-подписчик.

## 4. Устройство сервиса

```
services/catalog/
  src/
    main.ts                 HTTP (Fastify) + gRPC-сервер + подписки NATS в одном процессе
    app.module.ts
    http/                   контроллеры публичного API: контракт ⇄ сценарии
    grpc/                   реализация внутреннего API из proto
    events/                 публикация (через outbox) и обработчики входящих событий
    application/            сценарии (по файлу на сценарий), порты репозиториев и клиентов
    domain/                 сущности, value objects, доменные ошибки — без Nest, Prisma, gRPC
    infrastructure/         Prisma-репозитории, клиенты других сервисов, внешние API
  prisma/                   schema.prisma, migrations/, конфиг Prisma CLI
  seed.ts                   сид из @wine/demo-data
  test/                     интеграционные и e2e
  Dockerfile
```

- Зависимости внутри сервиса: `http | grpc | events → application → domain`; `infrastructure` реализует порты `application`. Домен не импортирует фреймворки и сгенерированный код контрактов.
- Для сервисов без правил (подписка на рассылку) слой `domain/` можно не заводить.
- Клиент другого сервиса — только за портом в `application/` (`WineCatalog`), реализация в `infrastructure/` с дедлайном, повтором и отображением ошибок. Сценарий решает, что делать при недоступности.

## 5. Данные

- **База на сервис** в одном кластере PostgreSQL (`catalog`, `news`, …), своя роль на сервис с правами только на свою базу. Сервисы не ходят в чужие базы ни при каких условиях, включая отчёты и миграции.
- Prisma-клиент, миграции и сиды — внутри сервиса: `prisma/schema.prisma`, `prisma.config.ts`, клиент генерируется в `src/infrastructure/prisma/generated` (в `.gitignore`, `build` и `typecheck` сервиса начинаются с `prisma generate`). Версии `prisma`, `@prisma/client`, `@prisma/adapter-pg` — точные (7.10.1).
- Миграции — `prisma migrate deploy` одноразовым контейнером перед запуском новой версии (цель `migrate` в `services/Dockerfile`: Prisma CLI — dev-зависимость и в прод-образ не попадает), только вперёд; удаление столбца — в два релиза. `SEED=true` — ещё и демо-данные (`dist/seed.js`, повторный запуск безопасен).
- Логика сида — функция (`seedCatalog(prisma)`), а скрипт её вызывает: тесты наполняют базу тем же кодом.
- Строка запроса и путь приходят строками, а в сгенерированных схемах — `z.int()`. Пайп `service-kit` приводит к числу и булеву только поля, у которых в схеме число или булево: slug «1988» остаётся строкой.
- **Transactional outbox:** событие пишется в таблицу `outbox` той же транзакцией, что и изменение данных; ретранслятор из `service-kit` публикует в JetStream (`FOR UPDATE SKIP LOCKED`). **Inbox:** id обработанного события сохраняется в той же транзакции, что и эффект, — обработчики идемпотентны. Доставка «хотя бы один раз».
- Ссылки на чужие сущности — по стабильному id (UUID), без внешних ключей. Нужно часто или для фильтрации — локальная копия (read model) по событиям владельца.
- Распределённых транзакций нет. Процесс из нескольких сервисов (бронь → оплата → выдача) — сага через события с компенсациями.

| Что | Правило |
|---|---|
| Первичные ключи | `uuid`, UUIDv7 (`@default(uuid(7))`) |
| Публичные адреса | Отдельный уникальный `slug` |
| Имена | Prisma — camelCase, БД — snake_case через `@map` / `@@map` |
| Время | `timestamptz` в UTC; календарные даты — `date` |
| Деньги | Целые копейки; в API — как в контракте |
| Email | `citext` |
| Списки | `limit/offset` по контракту; keyset — для больших лент |

## 6. Взаимодействие: что когда

| Нужно | Как |
|---|---|
| Показать пользователю данные одного сервиса | Публичный HTTP этого сервиса через Traefik |
| Дополнить ответ данными соседа (вино к статье) | Пакетный gRPC-вызов с дедлайном; при отказе — ответ без этих данных, если контракт позволяет |
| Отреагировать на изменение у соседа | Подписка на его событие |
| Часто читать чужие данные, фильтровать или сортировать по ним | Локальная копия по событиям |
| Изменение в нескольких сервисах | Сага на событиях, никаких синхронных цепочек записи |

Цепочки синхронных вызовов длиннее одного шага (A → B → C) запрещены: это распределённый монолит.

## 7. HTTP и безопасность

- Ошибки — в формате контракта `Error { code, message }` (`message` — по-русски, для пользователя) + необязательный `details`. Тело — 422, путь и query — 400, нет сущности — 404 `not_found`, принято в обработку — 202, идемпотентно без тела — 204.
- GET публичного контента — короткий `Cache-Control` и `ETag`; персональное — `no-store`. Лимит тела — 64 КБ.
- **Аутентификация на краю.** Сессия — httpOnly-cookie `__Host-` (`Secure`, `SameSite=Lax`). Traefik для защищённых путей вызывает `identity` (forward-auth) и передаёт в сервис заголовок с id пользователя; входящие снаружи такие заголовки шлюз вырезает. Сервисы внешним заголовкам без шлюза не доверяют: сеть сервисов закрыта.
- **CORS.** Фронт — на GitHub Pages, API — на VPS, это разные origin. Traefik разрешает только origin фронта (allowlist, `credentials: true`), preflight кэшируется. Чтобы httpOnly-cookie сессии работали (браузеры режут сторонние cookie), фронт и API должны быть на одном сайте: свой домен для Pages (`example.ru`) и `api.example.ru` для API, cookie с `SameSite=Lax`. На `*.github.io` вход работать не будет — это нужно решить до фазы 8.
- CSRF: проверка `Origin` у мутирующих запросов на шлюзе (тот же allowlist).
- Лимиты частоты для публичных форм — на шлюзе; при спаме — Yandex SmartCaptcha.
- **152-ФЗ:** ПДн только в российском облаке, согласия фиксируются с версией текста и временем, IP и user-agent без цели не храним, в логах и событиях ПДн маскируются или не передаются.
- Секреты — из окружения (панель провайдера, Kubernetes Secrets, GitHub Secrets); конфиг валидируется zod при старте.

## 8. Наблюдаемость и устойчивость

- OpenTelemetry во всех сервисах: трейс проходит Traefik → HTTP → gRPC → NATS (контекст в заголовках CloudEvents). Логи pino с `traceId`, `spanId`, `service`.
- Пробы: `/health/live` (процесс жив), `/health/ready` (БД и брокер доступны). Корректное завершение: перестать принимать запросы, дождаться текущих, остановить ретранслятор outbox, закрыть пулы.
- Метрики RED (частота, ошибки, задержки) по HTTP и gRPC, длина очередей JetStream и outbox.
- Ошибки — в GlitchTip (совместим с Sentry SDK, разворачивается у себя).

| Уровень | Что | Чем |
|---|---|---|
| Юнит | Домен и сценарии с подменёнными портами | Vitest |

## 10. Сборка и деплой

- Turborepo: `turbo run build lint test` локально — кэш задач, сборка только затронутого. **CI для бэкенда пока нет** (решение 18.10.2026): проверки сервисов запускаются локально перед пушем; GitHub Actions для `services/*` добавим позже — по плану из §9.
- Сборка: общие пакеты (`@wine/service-kit`, zod-схемы и раскладка операций в `@wine/contracts`) компилируются `tsc` в `dist` — Node не исполняет `.ts` из `node_modules`, а в образе пакеты лежат именно там. Сервисы собираются Nest CLI (сборщик tsc, ESM). Общая база — `tsconfig.service.json` в корне. В `package.json` пакетов есть `files`, иначе `pnpm deploy` не возьмёт `dist`.
- Образ — один `services/Dockerfile` на все сервисы (`--build-arg SERVICE=<имя>`): `pnpm fetch` по lockfile, сборка через Turborepo, `pnpm deploy --prod --legacy`, запуск не от root, `HEALTHCHECK` на `/health/ready`.
- OpenTelemetry — `node --import @wine/service-kit/telemetry dist/main.js`: те же автоинструментации, что у `auto-instrumentations-node/register`, и те же переменные `OTEL_*` (`OTEL_SDK_DISABLED=true` — выключено), но без шума — пробы `/health/*` (Docker и Traefik дёргают их каждые несколько секунд), `fs`, `dns`, `net` не трассируются. Без фильтра 44 из 50 трейсов были пробами. Трейсинг Traefik (`--tracing.otlp`) включается вместе с профилем `observability` (`TRAEFIK_TRACING=true`).
- Разработка: `pnpm backend:up` — `deploy/compose/compose.yaml` (Postgres на порту хоста **55432** — 5432 часто занят локальным Postgres; база и роль на сервис, NATS JetStream, Traefik с маршрутами из `deploy/traefik/dynamic.yml`, сервисы); API — на `http://localhost:8080/api`. Наблюдаемость — профиль `observability` (`grafana/otel-lgtm`, Grafana на :3001). Фронт с `VITE_API_MOCKS=false` ходит туда через Vite proxy.
- Маршруты Traefik — файловым провайдером, а не метками Docker: шлюзу не нужен доступ к сокету Docker. Новый сервис — новый роутер в `dynamic.yml` по раскладке `OPERATION_OWNERS` из контрактов.
- Прод: Docker Compose на арендованном VPS у российского провайдера — Traefik (TLS от Let's Encrypt через ACME), сервисы, NATS, PostgreSQL 18 с бэкапами (WAL-G в S3-совместимое хранилище) и наблюдаемость. Выкатка — `docker compose pull && up -d` с тегом образа, миграции — одноразовый контейнер перед запуском сервиса. Потом, если понадобится, — управляемый PostgreSQL и Managed Kubernetes с Helm; код сервисов при переходе не меняется.
- Docker Hub из России доступен нестабильно: на VPS — зеркало реестра провайдера; свои образы собираются на VPS или пушатся в реестр провайдера.

## 11. Чек-листы

**Новый публичный эндпоинт:** OpenAPI в `@wine/contracts` → `pnpm contracts:gen` → сценарий в сервисе-владельце → контроллер со схемами входа и выхода → маршрут в Traefik (если новый префикс) → тесты → MSW-обработчик во фронте.

**Сервису нужны чужие данные:** есть пакетный метод в proto владельца? → клиент за портом, дедлайн, деградация. Нет → добавить метод в proto владельца (обратно совместимо). Нужно часто или для фильтрации → локальная копия по событиям.

**Новое событие:** схема в `contracts/events` → публикация через outbox в той же транзакции → подписчик с inbox → тест совместимости схемы.

**Новый сервис:** только если появился новый ограниченный контекст. Шаблон из `services/*`, своя база и роль, поток JetStream, маршрут в Traefik, строка в карте сервисов плана.
