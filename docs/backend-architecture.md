# Бэкенд: правила архитектуры

Постоянные правила для `apps/api`. Этапы работ, карта модулей и модель данных — в [backend-plan.md](backend-plan.md). Если правило мешает, его меняют здесь и фиксируют причину, а не обходят в коде.

## 0. Принципы

1. **Модульный монолит, спроектированный как набор микросервисов.** Один процесс и один деплой, но каждый модуль — отдельный ограниченный контекст: свои данные, свой публичный интерфейс, никаких общих таблиц и глубоких импортов. Любой модуль можно вынести в отдельный сервис, заменив вызов фасада на HTTP или gRPC, а шину событий — на брокер, без переписывания бизнес-логики.
2. **Контракт сначала.** `openapi.yaml` — источник правды и для фронта, и для бэкенда. Бэкенд реализует контракт, а не порождает его. Ответ, не совпадающий со схемой, — ошибка сервера.
3. **Домен не знает про фреймворк.** Правила бизнеса — в чистом TypeScript, без Nest, Prisma и HTTP.
4. **Скучные надёжные решения.** Стабильные версии, официальные возможности фреймворка, минимум самописной инфраструктуры. RC и бета — не в продакшен.
5. **Работает из России.** Хостинг, БД, почта, SMS и хранилища — у российских провайдеров. Персональные данные хранятся в РФ (152-ФЗ).

## 1. Стек

Версии сверены с npm и документацией в октябре 2026. В `package.json` версии фиксируются точно (`save-exact`), обновления — через Renovate, а не руками.

| Что | Выбор | Почему |
|---|---|---|
| Рантайм | Node.js 24 LTS | Тот же, что в CI фронта. На 26 переходим, когда он станет LTS и выйдут образы |
| Фреймворк | NestJS 12 (ESM) | Модули и DI из коробки. В 12 появилась встроенная валидация по Standard Schema |
| HTTP-адаптер | Fastify 5 (`@nestjs/platform-fastify`) | Быстрее Express, нативная схема и логгер pino. Express нам ничего не даёт |
| Язык | TypeScript 6.0, `strict` | Nest CLI собран на TS 6.0, а typescript-eslint поддерживает < 6.1. TS 7 (нативный) — когда догонят инструменты |
| БД | PostgreSQL 18 | Текущий стабильный. UUIDv7 генерируем в приложении, чтобы не зависеть от минорной версии у провайдера |
| ORM | Prisma 7 (7.10.x), драйвер-адаптер `@prisma/adapter-pg` | Стабильная ветка. **Prisma 8 — RC**, а npm-тег `latest` у пакета `prisma` уже указывает на 8.0 RC: ставить только с точной версией |
| Валидация | Zod 4 + `StandardSchemaValidationPipe` / `StandardSchemaSerializerInterceptor` из Nest | Встроено в Nest 12, сторонние адаптеры (nestjs-zod) не нужны. Схемы генерируются из контракта |
| Генерация из контракта | `openapi-typescript` (типы `paths`, как во фронте) + `@hey-api/openapi-ts`, плагин zod (схемы запросов и ответов) | Один `openapi.yaml` → типы для фронта и MSW, zod-схемы для бэкенда |
| Логи | `nestjs-pino` (JSON, request id, маскирование ПДн) | Стандарт для Fastify |
| Здоровье | `@nestjs/terminus` | `/api/health/live`, `/api/health/ready` (с БД) |
| Защита | `@fastify/helmet`, `@nestjs/throttler`, `@fastify/cookie` | |
| Документация API | Scalar (`@scalar/fastify-api-reference`) по тому же `openapi.yaml` | Swagger-декораторы не пишем: контракт уже есть |
| Тесты | Vitest 5 (по умолчанию в Nest 12 ESM), Testcontainers (`@testcontainers/postgresql`) | Тесты репозиториев и e2e — на настоящем Postgres, без моков БД |
| Линтер | ESLint (flat config, как во фронте) + typescript-eslint + `eslint-plugin-boundaries` | Границы модулей проверяются при каждом сохранении. Nest 12 по умолчанию предлагает oxlint, но плагина границ модулей у него нет |
| Архитектурные проверки | `dependency-cruiser` | Циклы между модулями и граф зависимостей в CI |
| Проверка контракта | `oasdiff` | Ломающие изменения `openapi.yaml` видны в CI |
| Монорепозиторий | pnpm workspaces | Двух приложений и пары пакетов хватает без Turborepo и Nx. Добавим, когда CI станет долгим |

## 2. Репозиторий

```
apps/
  web/                     фронтенд (нынешний корень репозитория)
  api/                     бэкенд NestJS
packages/
  api-contract/            openapi.yaml + сгенерированное: schema.ts (типы paths) и zod-схемы
  demo-data/               демо-данные из макетов: фикстуры MSW во фронте и сиды БД в бэкенде
deploy/                    nginx фронта, docker compose для локальной разработки
docs/
```

- Пакеты подключаются как `workspace:*`: `@wine/api-contract`, `@wine/demo-data`.
- `apps/web` и `apps/api` друг друга не импортируют. Общее у них — только пакеты.
- Демо-данные одни на фронт и бэк. Плейсхолдеры дизайна (`[Имя гостя]`, `[цена]`) остаются плейсхолдерами и в БД.

## 3. Контракт API

- Источник правды — `packages/api-contract/openapi.yaml` (OpenAPI 3.1). Новый эндпоинт: сначала контракт, потом `pnpm api:gen`, потом реализация на обеих сторонах.
- Сгенерированные файлы коммитятся. CI перегенерирует их и падает, если есть расхождение (`git diff --exit-code`).
- **Каждый обработчик объявляет схемы из контракта** — и на вход, и на выход:
  - вход — `@Body({ schema })`, `@Query({ schema })`, `@Param({ schema })`, глобально включён `StandardSchemaValidationPipe`;
  - выход — `@SerializeOptions({ schema })` при глобальном `StandardSchemaSerializerInterceptor`. Схема ответа работает как allowlist: лишние поля отрезаются, а несоответствие даёт 500 и попадает в лог как баг.
- Тест покрытия контракта: у каждого `operationId` из `openapi.yaml` есть обработчик с тем же методом и путём, и наоборот.
- Изменения контракта — только обратно совместимые (новые необязательные поля, новые эндпоинты). Ломающее изменение — отдельная задача с одновременной правкой фронта, `oasdiff breaking` в CI его подсвечивает.
- Префикс `/api` (как `servers.url` в контракте), версии в пути нет. Появится ломающее изменение — `/api/v2` для затронутых эндпоинтов.
- JSON — camelCase, как в контракте. Даты — ISO 8601 (`format: date` → `YYYY-MM-DD`, `date-time` — с часовым поясом).

## 4. Модули

### 4.1 Что такое модуль

Модуль — ограниченный контекст: каталог, газета, отзывы. Внутри модуля — его данные, правила и HTTP-эндпоинты. Наружу модуль отдаёт только **публичный интерфейс**:

- **фасад** — абстрактный класс (он же DI-токен), например `CatalogApi`, с асинхронными методами;
- **контрактные типы фасада** — простые сериализуемые DTO и их zod-схемы;
- **интеграционные события**, которые модуль публикует: имя с версией (`catalog.wine-changed.v1`) и zod-схема полезной нагрузки;
- **Nest-модуль**, который экспортирует только фасад.

Всё это экспортирует `src/modules/<module>/index.ts`. Всё остальное — внутреннее.

### 4.2 Структура

```
src/
  main.ts
  app.module.ts             собирает platform и модули, больше ничего
  platform/                 сквозная инфраструктура, не бизнес
    config/                 переменные окружения (zod), без значений по умолчанию для секретов
    http/                   фильтр ошибок, пайпы, перехватчики, cookies, CSRF
    database/               база для Prisma-клиентов модулей, транзакции
    messaging/              шина событий, outbox, inbox
    logging/  health/  security/
  modules/
    catalog/
      index.ts              ПУБЛИЧНЫЙ интерфейс: CatalogModule, CatalogApi, contracts/*, events/*
      catalog.module.ts     exports: [CatalogApi] — и только его
      contracts/            DTO и zod-схемы фасада (чистый TS, без импортов изнутри модуля)
      events/               схемы публикуемых событий
      api/                  контроллеры: контракт ⇄ команды и запросы application-слоя
      application/          сценарии (по файлу на сценарий), порты репозиториев, реализация фасада
      domain/               сущности, value objects, доменные ошибки — без Nest и Prisma
      infrastructure/       Prisma-репозитории, адаптеры внешних сервисов
      prisma/               schema.prisma (только модели модуля), migrations/, конфиг CLI
      seed.ts               сид из @wine/demo-data
      *.spec.ts             юнит-тесты рядом с кодом; *.int-spec.ts — с настоящей БД
test/e2e/                   e2e и контрактные тесты всего приложения
```

- **Направление зависимостей внутри модуля:** `api → application → domain`, `infrastructure → application/domain` (реализует порты). Домен не импортирует ничего, кроме себя и `platform/kernel` (базовые классы ошибок, Result, Clock).
- **Упрощение для простых модулей.** Если правил почти нет (подписка на рассылку, справочник), слой `domain/` можно не заводить: сценарий в `application/` работает с репозиторием. Публичный интерфейс и собственные данные обязательны всегда.
- Имена модулей — существительные контекста в единственном числе или устойчивые названия: `catalog`, `grapes`, `news`, `reviews`, `newsletter`, `identity`. Совпадают с именем схемы в Postgres.

### 4.3 Правила импорта

1. Из другого модуля импортируется только его `index.ts` (`@modules/catalog`). Глубокие импорты (`@modules/catalog/infrastructure/...`) запрещены.
2. `platform/` не импортирует модули. Модули импортируют `platform/` свободно.
3. Граф модулей ацикличен. Если двум модулям нужно знать друг о друге — один вызывает фасад, второй узнаёт новости через событие.
4. `domain/` не импортирует `@nestjs/*`, `@prisma/*`, `fastify`, `zod` из контракта и сгенерированный Prisma-клиент.
5. Prisma-клиент модуля доступен только его `infrastructure/`.
6. Всё это проверяют `eslint-plugin-boundaries` (в редакторе и `pnpm lint`) и `dependency-cruiser` (в CI). Нарушение — красный CI, а не предупреждение.

### 4.4 Синхронное взаимодействие — фасады

Фасад проектируется так, будто это удалённый API:

- методы асинхронные, принимают и возвращают **простые сериализуемые DTO** (никаких сущностей, Prisma-моделей, классов с методами, `Date` — только ISO-строки);
- методы **крупные и пакетные**: `getWineSummaries({ ids })` вместо вызова в цикле — иначе после выноса в сервис получится N+1 по сети;
- ошибки — типизированный результат или доменные ошибки из `contracts/`, не HTTP-исключения;
- **никаких общих транзакций**: вызов фасада не участвует в транзакции вызывающего модуля;
- изменение сигнатуры фасада — как изменение публичного API: сначала добавить новое, потом убрать старое.

```ts
// modules/catalog/index.ts — так выглядит публичный интерфейс
export { CatalogModule } from "./catalog.module";
export { CatalogApi } from "./application/catalog.api";      // abstract class = DI-токен
export type { WineSummaryDto } from "./contracts/wine-summary";
```

### 4.5 Асинхронное взаимодействие — события

- Модуль публикует **интеграционные события** о фактах: «письмо получено», «вино изменилось». Имя `<модуль>.<факт-в-прошедшем>.v<N>`, полезная нагрузка — zod-схема из `events/`.
- **Transactional outbox:** событие пишется в таблицу `outbox` своей схемы в той же транзакции, что и изменение данных. Ретранслятор из `platform/messaging` забирает записи (`FOR UPDATE SKIP LOCKED`) и раздаёт обработчикам. Доставка — «хотя бы один раз».
- **Обработчики идемпотентны:** id обработанного события пишется в `inbox` модуля-получателя в той же транзакции, что и его эффект.
- Сейчас шина работает в процессе. При выносе модуля её заменят на брокер (NATS JetStream или RabbitMQ), а схемы событий и outbox останутся.
- Outbox появляется вместе с первым событием, у которого есть подписчик, а не заранее.

### 4.6 Чтение данных из нескольких модулей

- Ссылка на чужую сущность — только её **стабильный id** (UUID). Внешних ключей между схемами нет.
- Собрать ответ из данных нескольких модулей (сорт винограда и его вина) — задача модуля-владельца эндпоинта: он берёт свои данные и одним пакетным вызовом фасада дочитывает чужие.
- Если чужие данные нужны часто и для поиска или сортировки — локальная копия (read model), обновляемая по событиям. Заводим, только когда фасада объективно не хватает.

## 5. Данные

- **Одна база, своя схема Postgres у каждого модуля** (`catalog`, `news`, …). Таблицы модуля живут только в его схеме.
- **Свой Prisma-клиент у каждого модуля:** `prisma/schema.prisma` описывает только модели модуля, генератор `prisma-client` пишет клиент внутрь модуля (в `.gitignore`), миграции — в `prisma/migrations` модуля, история миграций — в его же схеме. Так модуль физически не может прочитать чужую таблицу через ORM, а вынос в сервис со своей базой — это смена строки подключения.
- Подключение — через `@prisma/adapter-pg`. Размер пула задаётся на модуль, суммарный бюджет соединений должен влезать в лимит управляемого Postgres. Позже — PgBouncer.
- Кросс-модульных транзакций нет. Внутри модуля — интерактивные транзакции Prisma, через Unit of Work из `platform/database`.
- **Миграции:** создаются `prisma migrate dev` на модуль, применяются `prisma migrate deploy` отдельным шагом перед выкаткой, а не при старте приложения. Миграции только вперёд. Опасные изменения (удаление столбца) — в два релиза: сначала код перестаёт его использовать.
- Позже, для жёсткой изоляции, можно завести роль Postgres на модуль с правами только на свою схему.

Соглашения по данным:

| Что | Правило |
|---|---|
| Первичные ключи | `uuid`, UUIDv7 (`@default(uuid(7))`) — упорядочены по времени, не раскрывают количество |
| Публичные адреса | Отдельный `slug` (уникальный), не id |
| Имена | Модели и поля Prisma — camelCase, в БД — snake_case через `@map` / `@@map` |
| Время | `timestamptz`, хранится в UTC. Календарные даты (выпуск газеты) — `date` |
| Деньги | Целые копейки (`integer`). В API — как в контракте (сейчас рубли) |
| Перечисления | Enum Prisma, совпадающие со значениями из контракта |
| Тексты | `text`, без искусственных `varchar(n)`. Длину ограничивает валидация |
| Email | `citext` (уникальность без учёта регистра) |
| Удаление | Физическое. Где нужна история — статус (`unsubscribed`, `rejected`), а не `deleted_at` везде подряд |
| Списки | `limit/offset`, как в контракте. Для больших лент — keyset-пагинация в новой версии эндпоинта |

## 6. HTTP

- **Ошибки** — всегда в формате контракта `Error { code, message }` (`message` на русском, для пользователя), плюс необязательный `details` для ошибок валидации. Доменные ошибки несут `code` и сопоставляются со статусом в `platform/http`.
- Ошибка валидации тела запроса — **422**, параметров пути и строки запроса — **400** (как в контракте). Нет сущности — 404 с `code: "not_found"`.
- Принятые на модерацию или в очередь данные — **202**, идемпотентные действия без тела — **204**.
- GET публичного контента (каталог, газета) отдаёт `Cache-Control` с коротким сроком и `ETag`. Персональные ответы — `no-store`.
- Лимит тела запроса — 64 КБ по умолчанию. Больше — только для загрузки файлов (когда появится).
- Сессия — httpOnly-cookie `__Host-` с `Secure` и `SameSite=Lax`. Мутирующие запросы проверяют `Origin` (защита от CSRF). Токены в теле ответа и в `localStorage` не отдаём.
- Фронт и API — на одном домене (nginx фронта проксирует `/api`), поэтому CORS не нужен и выключен.

## 7. Безопасность и персональные данные

- **152-ФЗ:** персональные данные (имена и города в письмах, email подписчиков, позже телефоны) хранятся только в российском облаке. Согласие на обработку фиксируется с версией текста и временем. Храним только нужное: IP и user-agent не сохраняем без явной цели.
- В логах ПДн маскируются (email, телефон, имя), тела запросов форм не логируются.
- Публичные формы (письмо, подписка) ограничены по частоте (`@nestjs/throttler`). При спаме — Yandex SmartCaptcha.
- Секреты — только из окружения (панель провайдера, GitHub Secrets), в репозитории — `.env.example` без значений. Конфиг валидируется zod при старте: нет обязательной переменной — приложение не стартует.
- Сырой SQL — только через параметризованные `$queryRaw` и TypedSQL.
- Зависимости обновляются через Renovate. `pnpm audit` в CI не блокирует сборку, но выводится в отчёт.

## 8. Наблюдаемость

- Структурированные JSON-логи (pino) с `requestId` (из `x-request-id` или новый) и именем модуля. Уровень — из окружения.
- `/api/health/live` — процесс жив. `/api/health/ready` — есть соединение с БД. Их использует платформа и `HEALTHCHECK` образа.
- Корректное завершение: `enableShutdownHooks`, ретранслятор outbox останавливается, пулы закрываются.
- Трассировка (OpenTelemetry) и сбор ошибок (самостоятельный GlitchTip или Sentry) — отдельным этапом, когда появится продакшен-трафик.

## 9. Тесты и проверки

| Уровень | Что проверяем | Чем |
|---|---|---|
| Юнит | Домен и сценарии с подменёнными портами | Vitest |
| Интеграционные | Репозитории и миграции модуля на настоящем Postgres | Vitest + Testcontainers (`postgres:18-alpine`) |
| E2E и контракт | Приложение целиком: ответы проходят zod-схемы контракта, все `operationId` реализованы | Vitest + Fastify `inject` + Testcontainers |
| Архитектура | Границы модулей, отсутствие циклов, фасад — единственный экспорт Nest-модуля | ESLint boundaries, dependency-cruiser, тест на метаданные модулей |
| Контракт | Сгенерированное актуально, нет непредусмотренных ломающих изменений | `pnpm api:gen` + `git diff`, `oasdiff` |

Фронт продолжает тестироваться на MSW: моки и бэкенд опираются на одни и те же схемы и демо-данные.

## 10. Конфигурация, сборка, деплой

- Окружения: `development` (docker compose: Postgres + API, фронт через Vite proxy), `test` (Testcontainers), `production`.
- Docker-образ API: многостадийная сборка на `node:24-alpine`, `pnpm deploy --prod` только с зависимостями API, запуск не от root, `HEALTHCHECK` на `/api/health/ready`.
- Миграции — отдельная команда (`pnpm --filter api db:migrate:deploy`) шагом релиза перед запуском новой версии.
- Прод: фронт и API — отдельные приложения (контейнеры) у одного российского провайдера, управляемый PostgreSQL с бэкапами и PITR. nginx фронта проксирует `/api/` на внутренний адрес API (адрес — из переменной окружения через шаблон nginx), так что CSP `connect-src 'self'` не меняется.
- Docker Hub из России доступен нестабильно: локально и в облаке используем зеркало реестра провайдера. В GitHub Actions — напрямую.

## 11. Чек-листы

**Новый эндпоинт:** контракт в `openapi.yaml` → `pnpm api:gen` → сценарий в `application/` (+ домен) → репозиторий → контроллер со схемами входа и выхода → интеграционный и e2e-тест → MSW-обработчик во фронте на тех же демо-данных.

**Новый модуль:** папка по структуре 4.2 → своя схема Postgres и Prisma-клиент → `index.ts` с фасадом и типами → правила `eslint-plugin-boundaries` подхватывают его по шаблону пути → строка в карте модулей [backend-plan.md](backend-plan.md) (данные, фасад, события, зависимости).

**Модулю нужны чужие данные:** есть метод фасада? → вызвать пакетно. Нет → добавить метод в фасад владельца (это изменение его публичного API). Нужно часто, для фильтрации или сортировки → read model по событиям владельца.
